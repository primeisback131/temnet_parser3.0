# Temnet Parser: как здесь работать

Аналитика хелпдеск-переписки ejabberd. Устройство кодовой базы -
`docs/ARCHITECTURE.md`, методология метрик - `docs/METRICS.md`, запуск и
переменные окружения - `README.md`. Читать по мере надобности, перед правкой
соответствующего модуля, а не целиком на старте.

## Карта

| Что | Где |
|---|---|
| Backend: Spring Boot, порт 8080, весь API под `/api` | `backend/temnet_parser_3.0` |
| SQL метрик (не в Java-коде) | `src/main/resources/sql/*.sql` |
| Схема аналитической БД | `src/main/resources/analytics/schema.sql` |
| Frontend: React + antd + ECharts, порт 5173 | `frontend-react` |
| Единственный источник цвета | `frontend-react/src/lib/palette.ts` |
| Смоук фронтенда | `frontend-react/e2e/smoke.spec.ts` |

## Проверка

- Backend: `./gradlew test` в `backend/temnet_parser_3.0`. Нужна MariaDB
  `root:root@localhost:3306` с базой `ejabberd`.
- Frontend: `npm run build` (tsc + Vite) и `npm test` (собирает и гоняет
  смоук в Chromium: экран входа и каждая страница под администратором,
  API замокан, консоль должна быть чистой). Зелёный `tsc` не значит, что
  страница рендерится.
- Живые LLM-тесты включаются `CLAUDE_CLI_LIVE=1`; CI их не гоняет.
- Commit subject на английском, повелительное наклонение, без точки:
  `Fix empty ranking bars on the operators page`.

## Правила и их происхождение

- **Цвет только из `palette.ts`.** Ни одного hex в компонентах и
  страницах; потребители токенов - `theme.tsx`, `lib/antdTheme.ts`,
  `lib/chartTheme.ts`. Новый цвет - новый токен. Появилось в августе 2026
  после тёмной темы: разбросанные hex дали белый сайдбар на тёмном фоне.
- **Текст интерфейса: дефис, не тире; без воды.** Подсказка несёт число
  или дату, а не объяснение того, что видно и так. Русская проза в `docs/`
  сохраняет тире.
- **Схема только аддитивная.** `CREATE TABLE IF NOT EXISTS`,
  `ADD COLUMN IF NOT EXISTS`, без DROP, переименований и сужения типов:
  `schema.sql` накатывается на живую офисную базу при каждом старте.
- **Слои и SQL:** `docs/ARCHITECTURE.md`, раздел 9. Контроллер не ходит в
  репозиторий, SQL в ресурсах с именованными параметрами, даты на границе
  API как `yyyy-MM-dd`, внутри запросов полуинтервал `[start, end+1)`.
- **Не запускать второй backend.** Пользователь держит свой `bootRun` с
  DevTools; компиляция из другого шелла перезапускает его, а второй
  экземпляр падает на занятом 8080. Проверять через `curl` к работающему
  экземпляру или юнит-тестами. Осиротевший JVM от Gradle-демона может
  держать 8080 и выглядеть как «backend не стартует» (2026-09-02).
- **Claude CLI и подписка.** Пользовательская переменная
  `ANTHROPIC_API_KEY` переводит `claude` на потокенную оплату.
  `ClaudeCliChat` вырезает её из окружения дочернего процесса, это
  намеренно. Запуская `claude` из шелла от имени владельца, добавлять
  `env -u ANTHROPIC_API_KEY`. Интерактивные сессии делят одно 5-часовое
  окно с классификатором, загрузка около 40% во время работы - норма.
- **Время дампа читается в поясе сессии.** `archive.created_at` - TIMESTAMP,
  MariaDB отдаёт её в поясе сервера БД, поэтому одинаковый дамп на офисном
  сервере давал 19% сообщений «вне рабочего времени» против 4% локально
  (2026-09-08). Пояс закреплён параметром `DUMP_TZ` (`+05:00`); метрики
  рабочих часов сравнивать только после полной пересборки на обеих машинах.
- **Бит исполняемости скриптов задаётся через git.** На Windows
  `core.fileMode=false`, поэтому `gradlew` уехал в репозиторий как 100644 и
  CI падал с `Permission denied` (2026-09-08). Новый shell-скрипт:
  `git update-index --chmod=+x <файл>` перед коммитом.
- **Баг только на офисных VM через RDP** - сначала подозревать
  `prefers-reduced-motion` и другие RDP-специфичные media queries (попапы
  antd уезжали за экран, снято в de6bc12), потом сеть.
- **Краевые случаи:** сначала оценка вероятности, потом решение об объёме
  обработки. Очень редкий край - без кодового пути, но с `log.warn` и
  контекстом; про деньги, доступ и данные - падать громко и не терять
  молча. Отложенный край помечается `// TODO(...)` и строкой «не в этом
  коммите» в теле коммита, а не тихим усечением.

## Ветки и деплой

`main` - деплоируемая ветка без LLM; `feature/llm-classification` несёт
LLM-работу. Фикс: коммит на `main`, push, merge `main` в feature-ветку,
push. Офисный сервер (192.168.228.21, снаружи как 10.77.77.116:55173)
забирает `git pull` и перезапускает `run_frontend_prod.bat`; backend
перезапускается только при Java-изменениях.

## Приёмка

«Готово» - это перечень закрытых пунктов, а не зелёная сборка и не
уверенность автора. Для любого нетривиального изменения блок идёт в тело
коммита (PR здесь не заводятся) и перечитывается перед каждым коммитом:

```
Приёмка
- [x] сборка и тесты: ./gradlew test, npm test - <итог>
- [x] независимая проверка: <чем именно: curl, SQL в базе, второй расчёт; не «агент проверил»>
- [x] регрессионный тест на фикс: <file:line, красный до, зелёный после> или N/A
- [x] схема совместима с живой базой: <аддитивный ALTER / N/A>
- [ ] проверено в браузере на офисном стенде: PENDING
```

Правила вокруг блока:

- Открытый обязательный пункт называется PENDING наверху ответа, не в
  сноске. «Скорее всего в порядке» = не проверено = открыто.
- Фикс бага несёт тест, который видели красным до фикса. Нет тестовой
  поверхности (вёрстка, RDP-специфика) - словами, что и как проверено руками.
- Правки денег, доступа, схемы и ручного SQL выносятся в блок
  «Требует проверки человеком» с `file:line`, даже если коммит мелкий.
- Каждое новое правило в этом файле приходит с происхождением: одна-две
  строки о том, что случилось. Правило без причины первым пойдёт под нож.
