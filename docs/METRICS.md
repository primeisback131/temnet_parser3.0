## Обозначения

- **𝑀** — множество строк `message` в окне `[start, end+1день)`;
  **𝑇** — множество тикетов `ticket`.
- Для сообщения **m**: **t(m)** — время (`created_at`); **a(m)** — автор;
  **d(m) ∈ {in, out}** — направление; **txt(m)** — текст.
- Для тикета **T**: `opened_at`, `closed_at`, `status ∈ {open, closed,
  rejected, expired}`, `frt_seconds`, `resolution_seconds`, `category`,
  `reopen_score`, `reopen_llm`.
- **|·|** — количество; **Σ** — сумма; **mean(X)** = (1/|X|)·Σₓ x;
  **⌊·⌋** — целая часть.
- **Рабочее время.** Операторы работают **Пн–Пт, 08:00–18:00** (10 ч/день).
  Все интервалы time-метрик (FRT, время решения, границы заявок) меряются в
  **рабочих секундах** функцией `business_seconds(a, b)` — ночи (18:00–08:00)
  и выходные исключены. Поэтому, например, сообщение в 17:55 и ответ в 08:05
  следующего утра — это ~10 рабочих минут, а не ~14 часов.
- **Отсечки-выбросы** (в рабочих секундах): FRT учитывается при
  `frt ≤ 10 ч` (один рабочий день), время решения — при `≤ 50 ч`
  (пять рабочих дней). Значения выше считаются ошибочной склейкой и в
  перцентили/средние не попадают.

## Общие понятия

**Всё считается по аналитической БД.** Метрики не разбирают сырой архив
ejabberd на каждый запрос — фоновая синхронизация уже разложила его по
таблицам `message` (нормализованные сообщения) и `ticket` (заявки). Как
устроен инжест — дедупликация MAM-копий по stanza id, восстановление автора,
стейт-машина тикетов — описано в
[ARCHITECTURE.md, раздел 5](ARCHITECTURE.md#5-синхронизация-и-тикеты).
Здесь важно только то, что:

- в `message` каждая строка — одно реальное сообщение диалога клиент ↔
  поддержка, с настоящим автором и направлением (`in` — клиент, `out` —
  оператор); служебные MAM-строки и дубли уже отброшены;
- в `ticket` каждая строка — заявка с жизненным циклом
  `open → closed / rejected / expired`, открытая сообщением клиента и
  закрытая статус-фразой оператора; FRT и время решения посчитаны при
  инжесте в рабочих секундах.

**Статус-фразы заявок** (поиск по `LOWER(txt)` исходящих сообщений):

| Статус | Условие |
| --- | --- |
| Закрыта | `закрыта заявка` / `заявка закрыта` |
| Отклонена | `отклонена заявка` / `заявка отклонена` |
| В работе | `заявка в работе` / `в работе заявка` |

**Диапазон дат.** Параметры `start`/`end` — ISO `yyyy-MM-dd`. Везде
используется полуинтервал `created_at >= :start AND created_at < :end+1день` —
конечный день включён целиком.

**Атрибуция к группе.** Членство хранится в `client_group` (копия `sr_user`).
Фильтр по группе — `EXISTS`-проверка, что **клиент** диалога состоит в группе;
клиент, состоящий в нескольких группах, считается в объёмных метриках один раз.
Служебные группы `help%` и `all` исключаются.

**Кэш.** Ответы метрик кэшируются (Caffeine, TTL 10 мин) и сбрасываются после
каждой синхронизации с новыми данными.

## Статистика компаний — `/companies`

**Параметры:** `start`, `end`. **Возврат:** строка на группу.

Считается по клиентам группы: сообщения их диалогов с поддержкой (в обе
стороны) и исходы их заявок в периоде. Группы без единого сообщения в периоде
скрываются.

| Поле | Как считается |
| --- | --- |
| `activeUsers` | клиенты группы, в чьих диалогах были сообщения в периоде |
| `totalUsers` | всего клиентов в группе |
| `closedRequests` | заявки клиентов группы со статусом `closed` и `closed_at` в периоде |
| `rejectedRequests` | то же для `rejected` |
| `requestsInProgress` | заявки с отметкой «в работе» (`in_progress_at`) в периоде |
| `totalMessages` | сообщения диалогов клиентов группы в периоде |

**Математика.** Пусть `U_g` — клиенты группы `g`,
`M_u = { m ∈ 𝑀 : client(m) = u }`, `T_u` — тикеты клиента u:

```
totalMessages(g)      = Σ_{u∈U_g} |M_u|
closedRequests(g)     = |{ T ∈ T_u, u∈U_g : status=closed,  closed_at ∈ период }|
rejectedRequests(g)   = |{ T : status=rejected, closed_at ∈ период }|
requestsInProgress(g) = |{ T : in_progress_at ∈ период }|
activeUsers(g)        = |{ u ∈ U_g : M_u ≠ ∅ }|
totalUsers(g)         = |U_g|
```

## История чата — `/chat`

**Параметры:** `start`, `end`, `groupName`.
**Возврат:** сообщения `{sender, recipient, message, createdAt}`.

Отдаются сообщения диалогов всех клиентов группы, в хронологическом порядке.
Дедупликация и восстановление автора уже сделаны при инжесте, поэтому
`sender`/`recipient` — настоящие отправитель и получатель, и каждое сообщение
встречается один раз.

`GET /chat/chatlist` — множество уникальных участников переписки группы
(без операторов), для фильтра на экране.

## Динамика — `/metrics/timeseries`

**Параметры:** `start`, `end`, `bucket` (`day`/`week`/`month`), `groupName?`.
**Возврат:** точки `{bucket, messages, closed, rejected, inProgress}`.

Три слагаемых на бакет, каждое датируется своим событием:

- `messages` — сообщения по времени отправки;
- `closed` / `rejected` — заявки по времени **закрытия**;
- `inProgress` — заявки по времени отметки «в работе».

| `bucket` | SQL-усечение даты |
| --- | --- |
| `day` | `DATE(...)` |
| `week` | `DATE(... - INTERVAL WEEKDAY(...) DAY)` — понедельник недели |
| `month` | `DATE(DATE_FORMAT(..., '%Y-%m-01'))` — первое число месяца |

**Математика.** Пусть `bucket(x)` — усечение времени к началу бакета:

```
messages(b)   = |{ m ∈ 𝑀 : bucket(t(m)) = b }|
closed(b)     = |{ T : status=closed,   bucket(closed_at) = b }|
rejected(b)   = |{ T : status=rejected, bucket(closed_at) = b }|
inProgress(b) = |{ T : bucket(in_progress_at) = b }|
```

## Нагрузка (хитмап) — `/metrics/heatmap`

**Параметры:** `start`, `end`, `groupName?`. **Возврат:** ячейки
`{weekday, hour, messages}`.

```sql
SELECT WEEKDAY(created_at) AS weekday,  -- 0=Пн .. 6=Вс
       HOUR(created_at)    AS hour,     -- 0..23
       COUNT(*)            AS messages
FROM message ... GROUP BY weekday, hour
```

Значение ячейки — **сумма** сообщений за весь период для данного сочетания
день-недели × час.

**Режим «Среднее/день» (на фронте).** Сумма ячейки делится на число таких
дней недели в выбранном диапазоне (считается на клиенте: перебор дней
диапазона). Так получается «типичная» нагрузка, не зависящая от длины периода.

**Математика.** Для ячейки (w, h):

```
messages(w,h) = |{ m ∈ 𝑀 : weekday(t(m)) = w, hour(t(m)) = h }|

                            messages(w,h)
average(w,h)  = ───────────────────────────────────
                Nw,  где Nw = |{ день d ∈ [start,end] : weekday(d) = w }|
```

## Время первого ответа (SLA) — `/metrics/sla`

**Параметры:** `start`, `end`, `bucket`, `groupName?`. **Возврат:** точки
`{bucket, responses, avgSeconds, p50Seconds, p90Seconds}`.

**Метрика — First Response Time (FRT):** сколько клиент ждёт **первой** реакции
оператора. Считается **один раз на заявку**: `frt_seconds` — рабочие секунды
от открывающего сообщения заявки до первого исходящего в ней, посчитано
стейт-машиной при инжесте. Отскоки клиента внутри заявки новой точкой замера
не являются. Заявки без ответа (`frt_seconds IS NULL`) и выбросы
(`frt > 10 рабочих часов`) не учитываются.

Бакет заявки — по её `opened_at`, причём заявки, открытые в **выходные**,
относятся к ближайшему понедельнику: выходные нерабочие, рабочие часы такой
заявки начинаются в понедельник, и без сдвига крошечные субботние/воскресные
выборки рисовали на графике ложные пики (заявка, открытая в субботу и
отвеченная в обед понедельника, честно набирает 5–6 рабочих часов ожидания).

| Поле | Как |
| --- | --- |
| `responses` | число заявок с первым ответом |
| `avgSeconds` | `AVG(frt_seconds)` |
| `p50Seconds` | медиана — `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY frt_seconds)` |
| `p90Seconds` | 90-й перцентиль — `PERCENTILE_CONT(0.9) …` |

**Математика.** Пусть F_b = { frt(T) : bucket(opened_at(T)) = b,
frt(T) ≠ null, frt(T) ≤ T_cap }, T_cap = 10 рабочих часов:

```
responses(b)  = |F_b|
avgSeconds(b) = mean(F_b)
p50Seconds(b) = Pq(F_b) при q=0.5      p90Seconds(b) = Pq(F_b) при q=0.9
```

где **Pq** — непрерывный перцентиль (`PERCENTILE_CONT`) с линейной
интерполяцией: отсортировав F_b по возрастанию (x₍₀₎…x₍ₙ₋₁₎),

```
r = q·(n−1),   k = ⌊r⌋,   f = r − k
Pq = x₍ₖ₎ + f·( x₍ₖ₊₁₎ − x₍ₖ₎ )
```

Общий показатель в шапке — **взвешенное среднее**, равное обычному среднему по
всем замерам:

```
            Σ_b avgSeconds(b)·responses(b)
overall  = ─────────────────────────────────
                Σ_b responses(b)
```

> На реальных данных медиана ≈ 15 сек, а среднее ≈ 9 мин: половина клиентов
> получает ответ почти мгновенно, но длинный хвост тянет среднее вверх —
> поэтому перцентили информативнее среднего.

## Время решения — `/metrics/resolution`

**Параметры:** `start`, `end`, `bucket`, `groupName?`. **Возврат:** точки
`{bucket, resolved, avgSeconds, p50Seconds, p90Seconds}`.

Сколько заявка живёт от открытия до закрытия: `resolution_seconds` — рабочие
секунды от `opened_at` до `closed_at`, посчитано при инжесте. Учитываются
только заявки со статусом `closed` (отклонённые и истёкшие — нет), бакет — по
времени **закрытия**; закрытия в выходные относятся к ближайшему понедельнику
(до выходных доживают в основном длинные заявки недели, и без сдвига они
рисовали пики на маленьких субботних/воскресных выборках). Отсечка выбросов —
50 рабочих часов (пять рабочих дней): более долгие «решения» — почти всегда
неверно склеенные заявки.

Агрегаты те же, что в SLA: количество, среднее, p50, p90 (`PERCENTILE_CONT`).

## Повторные обращения — `/metrics/reopens`

**Параметры:** `start`, `end`, `bucket`, `groupName?`. **Возврат:** точки
`{bucket, closed, probable, confirmed}`.

**Повторное обращение (reopen)** — заявка, открытая тем же клиентом в течение
**10 рабочих часов** (один рабочий день) после закрытия его предыдущей заявки,
по той же проблеме. «По той же проблеме» определяется тремя сигналами,
посчитанными при инжесте:

- **маркерные слова** в первом сообщении («опять», «снова», «не помогло»,
  «та же», «всё ещё», «по-прежнему», «так и не», …) — +2 балла;
- **совпадение категории** с предыдущей заявкой (кроме «Другое») — +1 балл;
- **вердикт LLM** для кандидатов без единого сигнала (0 баллов): модель
  сравнивает тексты старой и новой заявки и отвечает, та же это проблема
  (`same`) или новая (`new`). Пока вердикта нет, кандидат в метрику не входит.

На бакет:

| Поле | Как |
| --- | --- |
| `closed` | закрытий (`closed`+`rejected`) в бакете — знаменатель доли |
| `probable` | заявки с любым сигналом: `reopen_score > 0` или LLM `same` |
| `confirmed` | сильный сигнал: `reopen_score ≥ 2` (маркерные слова) или LLM `same` |

Закрытия бакетируются по `closed_at`, реопены — по `opened_at` новой заявки.
Доля на фронте: `probable / closed` (и `confirmed / closed`).

## Аномалии — `/metrics/alerts`

**Параметры:** нет. **Возврат:** `{asOf, weekStart, alerts[]}`, где каждый
алерт — `{type, groupName, current, baseline, ratio}`.

Сравнивается **последняя неделя** данных (7 дней до максимального
`created_at` в базе) с **базлайном** — средним по предыдущим 8 неделям.
Два типа:

| `type` | Условие срабатывания |
| --- | --- |
| `message_spike` | сообщений за неделю ≥ 30 и ≥ 2× недельного базлайна группы |
| `sla_degradation` | заявок за неделю ≥ 10 и средний FRT ≥ 2× базлайна группы |

Пороги — константы в `MetricsRepository` (`SPIKE_MIN_MESSAGES = 30`,
`SPIKE_RATIO = 2.0`, `SLA_MIN_TICKETS = 10`, `SLA_DEGRADATION_RATIO = 2.0`).
Минимальные объёмы отсекают мелкие группы, где ×2 — это шум из трёх
сообщений. Алерты отсортированы по `ratio` убыванию.

**Математика.** Для группы g, недели W = [asOf−7д, asOf] и базлайна
B = [asOf−9нед, asOf−7д):

```
message_spike:    current = |M_g ∩ W|,  baseline = |M_g ∩ B| / 8
                  срабатывает при current ≥ 30 и current ≥ 2·baseline

sla_degradation:  current = mean{ frt(T) : T ∈ T_g, opened_at ∈ W }
                  baseline = mean{ frt(T) : opened_at ∈ B }
                  срабатывает при |{T : opened_at ∈ W}| ≥ 10 и current ≥ 2·baseline
```

## Лидерборд операторов — `/metrics/operators`

**Параметры:** `start`, `end`, `groupName?`. **Возврат:** строка на оператора
`{operator, messages, closed, rejected, clients, avgReplySeconds}`.

Три источника, склеенные по имени оператора:

| Поле | Как считается |
| --- | --- |
| `messages` | исходящие сообщения этого автора в периоде |
| `clients` | уникальные клиенты, кому он писал |
| `closed` / `rejected` | заявки, **закрытые этим оператором** (`closed_by`) в периоде |
| `avgReplySeconds` | средний FRT заявок, где он ответил **первым** (`first_responder`), по заявкам, открытым в периоде, с отсечкой 10 рабочих часов |

**Математика.** Для оператора o:

```
messages(o)        = |{ m ∈ 𝑀 : a(m) = o, d(m) = out }|
clients(o)         = |{ различных client(m) : a(m) = o }|
closed(o)          = |{ T : closed_by = o, status = closed,   closed_at ∈ период }|
rejected(o)        = |{ T : closed_by = o, status = rejected, closed_at ∈ период }|
avgReplySeconds(o) = mean{ frt(T) : first_responder = o, opened_at ∈ период, frt ≤ T_cap }
```

> ⚠️ `avgReplySeconds` — это **среднее время первого ответа** по заявкам
> оператора, та же величина, что в SLA, но в разрезе «кто ответил первым».
> Сортировка лидерборда — по закрытым заявкам, затем по сообщениям.

## Категории заявок — `/metrics/categories`

**Параметры:** `start`, `end`, `groupName?`. **Возврат:** строка на категорию
`{category, requests}`.

**Единица — заявка.** Категория присваивается при инжесте: каждое клиентское
сообщение получает ранг по словарю (первое совпавшее ключевое слово; меньший
ранг = выше приоритет), заявка хранит **лучший (минимальный) ранг** по всем
своим клиентским сообщениям. Без совпадений — «Другое». Метрика — простой
`GROUP BY category` по заявкам, открытым в периоде.

**Математика.** Для заявки T с клиентскими сообщениями S_in:

```
rank(m) = min { r : категория_r совпала с txt(m) },  или K+1 без совпадений
cat(T)  = name( min_{m∈S_in} rank(m) ),              name(K+1) = «Другое»

requests(c) = |{ T : cat(T) = c, opened_at ∈ период }|
```

**Словарь категорий** ([`CategoryRules`](../backend/temnet_parser_3.0/src/main/java/com/temnet/temnet_parser/support/CategoryRules.java), в порядке приоритета):

| Категория | Ключевые слова (подстроки `LOWER(txt)`) |
| --- | --- |
| 1С | `1с, 1c, зуп, бухгалт` |
| ЭЦП/Подпись | `подпис, эцп, сертификат, криптопро, кэп` |
| Касса/ККТ | `касса, кассе, атол, ккт, фискальн, эвотор` |
| Спец-ПО | `консультант, гарант, фомс, скзи, госуслуг` |
| Печать | `принтер, печат, картридж, сканер, мфу, kyocera` |
| Телефония | `телефон, атс, sip, сип, микросип, звон` |

## Известные нюансы и ограничения

1. **Две «скорости» — SLA и время решения.** SLA меряет ожидание первой
   реакции, resolution — весь путь заявки до закрытия. У лидерборда
   `avgReplySeconds` — тот же FRT, но в разрезе оператора-первоответчика.

2. **Границы заявок — эвристика.** Заявка открывается сообщением клиента и
   закрывается статус-фразой оператора; если оператор фразу не написал,
   заявка истечёт по тишине (20 рабочих часов) как `expired` и в
   resolution/reopens не попадёт. Короткое «спасибо» в течение 4 рабочих
   часов после закрытия новую заявку не открывает.

3. **Reopen-эвристика консервативна.** Кандидаты без маркерных слов и без
   совпадения категории уходят на LLM; пока вердикта нет (нет ключа, лимит
   исчерпан), они в метрике не участвуют — доля реопенов может слегка
   подрастать задним числом по мере классификации.

4. **«Другое» — заметная доля категорий.** Словарный подход ловит явные
   темы; часть обращений сформулирована иначе или вне словаря. Лечится
   расширением словаря.

5. **Среднее чувствительно к выбросам** даже с отсечками — для SLA и
   resolution смотреть p50/p90; средние приведены для полноты.

6. **Выходные.** Официально нерабочие, но небольшая активность в данных есть
   (дежурные ответы). Рабочее время в выходные не тикает, поэтому ответ,
   данный в субботу на субботнюю заявку, учитывается как 0 рабочих секунд;
   на графиках SLA и resolution выходных точек нет — открытия и закрытия
   Сб/Вс отнесены к понедельнику.

7. **Живой backlog** — заявки, оставшиеся `open` на конец данных; отдельной
   метрики по ним нет, но они видны в `/admin/sync/status` (разбивка тикетов
   по статусам).
