## Обозначения

- **𝑀** — множество сообщений `archive`, попавших в окно `[start, end+1день)`.
- Для сообщения **m**: **t(m)** — время (`created_at`); **u(m)** —
  отправитель (`username`); **d(m) ∈ {in, out}** — направление;
  **txt(m)** — текст.
- **Индикаторы статус-фраз**: `closed(m), rejected(m), inprog(m) ∈ {0,1}`
  — равны 1, если `LOWER(txt(m))` содержит соответствующую фразу.
- **Диалог 𝐶** — сообщения с одним `user_key`, упорядоченные по времени:
  m₁, m₂, …, mₙ (t(m₁) ≤ t(m₂) ≤ …).
- **|·|** — мощность множества (количество); **Σ** — сумма;
  **mean(X)** = (1/|X|)·Σₓ x; **⌊·⌋** — целая часть.
- **Константы**: T_cap = 8 ч = 28 800 с (отсечка времени ответа);
  G = 15 мин = 900 с (порог разрыва сессии).

## Общие понятия

**Направление и стороны диалога.** Каждое сообщение `archive` относится либо к
клиенту, либо к оператору поддержки:

- **Оператор (`out`)** — `username` относится к поддержке:
  `username LIKE 'help%'` (везде — операторские аккаунты начинаются с `help`).
- **Клиент (`in`)** — все остальные.
- **`user_key`** — идентификатор клиента в диалоге: если отправитель —
  оператор, то клиент это локальная часть `peer`, иначе сам `username`.

**Статус-фразы заявок** (поиск по `LOWER(txt)`):

| Статус | Условие |
| --- | --- |
| Закрыта | `LIKE '%закрыта заявка%' OR '%заявка закрыта%'` |
| Отклонена | `LIKE '%отклонена заявка%' OR '%заявка отклонена%'` |
| В работе | `LIKE '%заявка в работе%' OR '%в работе заявка%'` |

**Диапазон дат.** Параметры `start`/`end` — ISO `yyyy-MM-dd`. Граница конца
трактуется по-разному:

- **Базовые отчёты** (companies, users, chat): `created_at BETWEEN :start AND :end`
  — конечный день фактически обрезается на 00:00:00 (исторически).
- **Метрики** (timeseries, heatmap, sla, operators, categories):
  полуинтервал `created_at >= :start AND created_at < :end+1день` — конечный
  день включён целиком (корректно).

**Атрибуция к группе.** В отчётах companies/users/timeseries/heatmap группа —
это через членство в `sr_user` (джойн `sr_group → sr_user → archive`). В
sla/operators/categories группа задаётся опционально через
`EXISTS`-проверку, что клиент (`user_key`) состоит в группе.

## Группы — `/groups`

Список групп для выпадающих списков.

```sql
SELECT name FROM sr_group WHERE name NOT LIKE 'help%' AND name != 'all'
```

Исключаются служебные группы поддержки (`help%`) и `all`.

## Статистика компаний — `/companies`

**Параметры:** `start`, `end`. **Возврат:** строка на группу.

Джойн `sr_group → sr_user (члены) → archive` по
`SUBSTRING_INDEX(sr_user.jid,'@',1) = archive.username` — то есть считаются
**сообщения, отправленные членами группы**, и статус-фразы в них.

| Поле | Как считается |
| --- | --- |
| `activeUsers` | `COUNT(DISTINCT jid)` членов, у кого есть сообщения в периоде |
| `totalUsers` | всего членов группы (подзапрос) |
| `closedRequests` | `SUM(IF(<фраза «закрыта»>,1,0))` |
| `rejectedRequests` | `SUM(IF(<фраза «отклонена»>,1,0))` |
| `requestsInProgress` | `SUM(IF(<фраза «в работе»>,1,0))` |
| `totalMessages` | `COUNT(*)` сообщений членов группы в периоде |

**Математика.** Пусть `U_g` — члены группы `g`, а `M_g = { m ∈ 𝑀 : u(m) ∈ U_g }`
— их сообщения (член ↔ `SUBSTRING_INDEX(jid,'@',1) = u(m)`):

```
totalMessages(g)      = |M_g|
closedRequests(g)     = Σ_{m∈M_g} closed(m)
rejectedRequests(g)   = Σ_{m∈M_g} rejected(m)
requestsInProgress(g) = Σ_{m∈M_g} inprog(m)
activeUsers(g)        = |{ u ∈ U_g : ∃ m∈M_g, u(m)=u }|
totalUsers(g)         = |U_g|
```

Группы `help%` исключены.

## Статистика пользователей — `/users`

**Параметры:** `start`, `end`, `groupName`. То же, что companies, но
сгруппировано по `sr_user.jid` внутри одной группы. Поля: `userName`,
`closedRequests`, `rejectedRequests`, `requestsInProgress`, `totalMessages`.

**Математика.** Для пользователя u (член группы), `M_u = { m∈𝑀 : u(m)=u }`:
`totalMessages(u)=|M_u|`, `closedRequests(u)=Σ_{m∈M_u} closed(m)` (аналогично
`rejected`, `inprog`).

## История чата — `/chat`

**Параметры:** `start`, `end`, `username` (используется как **подстрока**).
**Возврат:** сообщения `{sender, recipient, message, createdAt}`.

Отбираются сообщения диалога, где одна сторона — `help`, а другая содержит
подстроку `:username`:

```sql
(username LIKE '%:username%' AND peer LIKE 'help%')
OR (username LIKE 'help%' AND peer LIKE '%:username%')
```

Дедупликация: `ROW_NUMBER() OVER (PARTITION BY LEAST/GREATEST(участники), txt ORDER BY created_at)`,
оставляется первое вхождение (`rn = 1`), затем `GROUP BY created_at`.

`GET /chat/chatlist` — те же данные, но возвращает множество уникальных
отправителей, исключая `help`.

## Динамика — `/metrics/timeseries`

**Параметры:** `start`, `end`, `bucket` (`day`/`week`/`month`),
`groupName?`. **Возврат:** точки `{bucket, messages, closed, rejected, inProgress}`.

Тот же джойн, что в companies (сообщения членов групп), но сгруппировано по
**временно́му бакету**:

| `bucket` | SQL-усечение даты |
| --- | --- |
| `day` | `DATE(created_at)` |
| `week` | `DATE(created_at - INTERVAL WEEKDAY(created_at) DAY)` — понедельник недели |
| `month` | `DATE(DATE_FORMAT(created_at, '%Y-%m-01'))` — первое число месяца |

На бакет: `messages = COUNT(*)`, статусы — `SUM(IF(<фраза>))`. Группы `help%`/`all`
исключены; при заданном `groupName` — фильтр `sr_group.name = :groupName`.
Полуинтервал по датам (конечный день включён).

**Математика.** Пусть `bucket(m)` — усечение времени t(m) к началу бакета
(см. таблицу), а `M_b = { m ∈ M_g : bucket(m) = b }`:

```
messages(b)   = |M_b|
closed(b)     = Σ_{m∈M_b} closed(m)
rejected(b)   = Σ_{m∈M_b} rejected(m)
inProgress(b) = Σ_{m∈M_b} inprog(m)
```

## Нагрузка (хитмап) — `/metrics/heatmap`

**Параметры:** `start`, `end`, `groupName?`. **Возврат:** ячейки
`{weekday, hour, messages}`.

```sql
SELECT WEEKDAY(created_at) AS weekday,  -- 0=Пн .. 6=Вс
       HOUR(created_at)    AS hour,     -- 0..23
       COUNT(*)            AS messages
... GROUP BY weekday, hour
```

Значение ячейки — **сумма** сообщений за весь период для данного сочетания
день-недели × час.

**Режим «Среднее/день» (на фронте).** Сумма ячейки делится на число таких
дней недели в выбранном диапазоне (считается на клиенте: перебор дней
диапазона). Так получается «типичная» нагрузка, не зависящая от длины периода.

**Математика.** Для ячейки (w, h):

```
messages(w,h) = |{ m ∈ 𝑀 : weekday(t(m)) = w, hour(t(m)) = h }|

                            messages(w,h)
average(w,h)  = ───────────────────────────────────
                Nw,  где Nw = |{ день d ∈ [start,end] : weekday(d) = w }|
```

`Nw` — сколько раз день недели `w` встречается в диапазоне.

## Время первого ответа (SLA) — `/metrics/sla`

**Параметры:** `start`, `end`, `bucket`, `groupName?`. **Возврат:** точки
`{bucket, responses, avgSeconds, p50Seconds, p90Seconds}`.

**Метрика — First Response Time (FRT):** сколько клиент ждёт **первой** реакции
оператора на новое обращение.

Алгоритм (оконные функции, на диалог `user_key`, упорядоченный по времени):

1. Каждое сообщение размечается на `in`/`out`.
2. **Начало обращения («burst-start»)** — сообщение клиента (`in`), у которого
   предыдущее сообщение было `out` или его не было (`LAG(direction)`).
3. **`next_out`** — время ближайшего ответа оператора **после** этого
   сообщения (`MIN(created_at)` по `out`-строкам во фрейме «1 FOLLOWING …»).
4. **FRT = `next_out − created_at`** (от **первого** сообщения обращения).
5. Отсечка: учитываются только `FRT ≤ 8 часов` (`maxFrtSeconds`) — чтобы
   ночные/межсессионные паузы не раздували метрику.

На бакет:

| Поле | Как |
| --- | --- |
| `responses` | число обращений с ответом |
| `avgSeconds` | `AVG(frt)` |
| `p50Seconds` | медиана — `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY frt) OVER (PARTITION BY bucket)` |
| `p90Seconds` | 90-й перцентиль — `PERCENTILE_CONT(0.9) …` |

**Математика.** В диалоге 𝐶 = (m₁,…,mₙ):

```
Начала обращений:   B = { i : d(mᵢ)=in и (i=1 или d(mᵢ₋₁)=out) }

Ближайший ответ:    next_out(i) = min { t(mⱼ) : j>i, d(mⱼ)=out }

Время ответа:       FRTᵢ = next_out(i) − t(mᵢ)
                    учитывается, если next_out(i) существует и FRTᵢ ≤ T_cap
```

Пусть F_b = { FRTᵢ : i∈B, bucket(mᵢ)=b, FRTᵢ ≤ T_cap } — все значения в бакете b:

```
responses(b) = |F_b|
avgSeconds(b) = mean(F_b) = (1/|F_b|) · Σ_{x∈F_b} x
p50Seconds(b) = Pq(F_b) при q=0.5      p90Seconds(b) = Pq(F_b) при q=0.9
```

где **Pq** — непрерывный перцентиль (`PERCENTILE_CONT`) с линейной
интерполяцией: отсортировав F_b по возрастанию (x₍₀₎…x₍ₙ₋₁₎),

```
r = q·(n−1),   k = ⌊r⌋,   f = r − k
Pq = x₍ₖ₎ + f·( x₍ₖ₊₁₎ − x₍ₖ₎ )
```

Общий показатель в шапке — **взвешенное среднее**, равное обычному среднему по
всем замерам:

```
            Σ_b avgSeconds(b)·responses(b)        1
overall  = ───────────────────────────────── = ────── · Σ_b Σ_{x∈F_b} x
                Σ_b responses(b)                  Σ_b |F_b|
```

> На реальных данных медиана ≈ 15 сек, а среднее ≈ 9 мин: половина клиентов
> получает ответ почти мгновенно, но длинный хвост тянет среднее вверх —
> поэтому перцентили информативнее среднего.

Группа (опц.) — `EXISTS`, что клиент состоит в группе.

## Лидерборд операторов — `/metrics/operators`

**Параметры:** `start`, `end`, `groupName?`. **Возврат:** строка на оператора
`{operator, messages, closed, rejected, clients, avgReplySeconds}`.

**Оператор** = `username LIKE 'help%'`.

| Поле | Как считается |
| --- | --- |
| `messages` | `COUNT(*)` исходящих сообщений оператора |
| `closed` | `SUM(<фраза «закрыта»>)` |
| `rejected` | `SUM(<фраза «отклонена»>)` |
| `clients` | `COUNT(DISTINCT client)` — уникальных клиентов |
| `avgReplySeconds` | средняя **задержка ответа** |

**Задержка ответа** считается так: для каждого `out`-сообщения, у которого
непосредственно предыдущее сообщение в диалоге — клиентское (`LAG(direction)='in'`),
берётся `gap = created_at − время_предыдущего_сообщения`, с отсечкой 8 ч.
То есть отсчёт идёт **от последнего сообщения клиента перед ответом**.

**Математика.** Множество ответов оператора o:

```
R_o = { mᵢ : u(mᵢ)=o, d(mᵢ)=out, d(mᵢ₋₁)=in, gapᵢ ≤ T_cap },
      где gapᵢ = t(mᵢ) − t(mᵢ₋₁)

messages(o)       = |{ mᵢ : u(mᵢ)=o, d(mᵢ)=out }|
closed(o)         = Σ_{u(mᵢ)=o, out} closed(mᵢ)
rejected(o)       = Σ_{u(mᵢ)=o, out} rejected(mᵢ)
clients(o)        = |{ различных клиентов, кому писал o }|
avgReplySeconds(o)= mean({ gapᵢ : mᵢ∈R_o })
```

> ⚠️ Это **не то же**, что SLA. SLA меряет от **первого** сообщения обращения,
> operators — от **последнего** перед ответом. Поэтому для одной группы за один
> период «время первого ответа» (SLA) и «средняя задержка ответа» (операторы)
> закономерно различаются (SLA обычно больше). См. [нюансы](#известные-нюансы-и-ограничения).

Группа (опц.) — `EXISTS`, что клиент состоит в группе.

## Категории обращений — `/metrics/categories`

**Параметры:** `start`, `end`, `groupName?`. **Возврат:** строка на категорию
`{category, requests}`.

**Единица — обращение (сессия), а не сообщение.** Сообщения клиента
группируются в сессии: пауза в диалоге **> 15 минут** (`SESSION_GAP_SECONDS`)
начинает новое обращение. Это соответствует тикету гораздо лучше, чем счёт
по сообщениям.

Алгоритм:

1. Разметка `in`/`out`, `user_key`; `LAG(created_at)` для разрыва.
2. `is_start = 1`, если предыдущего сообщения нет или разрыв > 15 мин;
   `session_id = SUM(is_start) OVER (диалог)`.
3. Каждому сообщению присваивается **ранг** категории (приоритетный `CASE` из
   словаря: первое совпавшее ключевое слово; меньший ранг = выше приоритет).
4. На сессию берётся `MIN(rank)` по всем клиентским сообщениям → **лучшая
   (наиболее приоритетная) совпавшая категория** за всё обращение.
5. Ранг → имя; `COUNT` обращений по категориям. Без совпадений — **«Другое»**.

**Математика.** В диалоге 𝐶 = (m₁,…,mₙ) сессии нарезаются по разрыву G:

```
Начало сессии:   start(i) = 1, если i=1 или t(mᵢ) − t(mᵢ₋₁) > G;  иначе 0
Номер сессии:    sid(i)   = Σ_{k≤i} start(k)
```

Сессия S = сообщения с одним (user_key, sid); S_in — её клиентские сообщения.
Ранг сообщения по словарю из K категорий (по приоритету r=1..K):

```
rank(m) = min { r : категория_r совпала с txt(m) },   или K+1, если совпадений нет
```

Категория обращения — наиболее приоритетная среди всех его клиентских сообщений:

```
cat(S) = name( min_{m∈S_in} rank(m) ),   где name(K+1) = «Другое»

requests(c) = |{ сессии S : cat(S) = c }|
```

**Словарь категорий** ([`CategoryRules`](../backend/temnet_parser_2.0/src/main/java/com/temnet/temnet_parser/support/CategoryRules.java), в порядке приоритета):

| Категория | Ключевые слова (подстроки `LOWER(txt)`) |
| --- | --- |
| 1С | `1с, 1c, зуп, бухгалт` |
| ЭЦП/Подпись | `подпис, эцп, сертификат, криптопро, кэп` |
| Касса/ККТ | `касса, кассе, атол, ккт, фискальн, эвотор` |
| Спец-ПО | `консультант, гарант, фомс, скзи, госуслуг` |
| Печать | `принтер, печат, картридж, сканер, мфу, kyocera` |
| Телефония | `телефон, атс, sip, сип, микросип, звон` |
| Почта | `почт, п/я, outlook, ящик, письм, mail` |
| Удалёнка | `vpn, впн, openvpn, rdp, удаленк, удалёнк, удаленн, удалённ` |
| Сеть | `интернет, wi-fi, вай-фай, роутер, сеть` |
| Программы/ПО | `эксель, excel, ворд, word, офис, office, браузер, гугл, хром, chrome, битрикс, миранда, vk teams, vkteams` |
| Доступ | `пароль, логин, доступ, заблокир, учетн, учётн` |
| Файлы/Диск | `файл, папк, диск, архив` |
| Оборудование | `компьютер, ноутбук, монитор, не включается, клавиатур, мышь, считыват` |
| **Другое** | (ничего не совпало) |

«Удалёнка» — намеренно только про VPN/RDP-доступ клиента к ресурсам компании;
инструменты, которыми поддержка подключается к клиенту (AnyDesk/TeamViewer/
энидеск), в эту категорию **не входят**.

**Калибровка порога 15 мин:** при нём число обращений (~27.5k за период) ≈
числу закрытых заявок (~24.7k) + ~10%, т.е. закрываемость ~90% — логично.
Порог настраивается константой `SESSION_GAP_SECONDS`.

## Известные нюансы и ограничения

1. **Идентификатор оператора — `help%` (унифицирован).** Во всех запросах
   оператор определяется по префиксу `username LIKE 'help%'`. Ранее SLA и
   история чата использовали подстроку `LIKE '%help%'`, что ошибочно
   относило к операторам клиентов с «help» внутри имени (например
   `*.chelplomba`); теперь исправлено.

2. **Две «скорости ответа».** SLA (`/metrics/sla`) меряет время первого ответа
   от начала обращения; лидерборд (`/metrics/operators`) — задержку от
   последнего сообщения клиента. Это разные показатели; названия разведены
   («Время первого ответа» vs «Ср. задержка ответа»).

3. **Модель отчётов companies/users.** Они считают сообщения и статус-фразы,
   **отправленные членами групп** (а не диалоги клиент↔help). Это отдельная от
   chat/sla/categories модель, унаследованная из исходного приложения.

4. **«Другое» ≈ 46%** в категориях — словарный подход ловит явные темы; часть
   обращений сформулирована иначе или вне словаря. Улучшается итеративным
   расширением словаря либо LLM-классификацией остатка.

5. **Среднее чувствительно к выбросам** даже с отсечкой 8 ч — для SLA смотреть
   p50/p90; для лидерборда перцентили пока не считаются.

6. **Граница диапазона** в базовых отчётах (`BETWEEN`) обрезает конечный день;
   в метриках используется корректный полуинтервал.
